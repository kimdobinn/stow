# Stow for Mac: architecture

A window app (Dock icon; keeps running with its window closed) that watches chosen YouTube channels for new long-form and
members-only videos, keeps an Inbox, and plays the morning's videos as an alarm. It stores no videos.

The project is generated by XcodeGen from `project.yml`, so never edit `Stow.xcodeproj` by hand.
After adding or removing files, regenerate it:

    cd mac && xcodegen generate
    xcodebuild -project Stow.xcodeproj -scheme Stow -derivedDataPath <own path> build   # or: test

## Modules and ownership

Each folder has exactly one owner. Owners may add files only inside their own folders.

Dependency rules:
- YouTube and Account depend only on Shared.
- Core depends on Shared and uses YouTube and Account only through `YouTubeService` and `AccountService`.
- UI depends on Shared and on `AppModel`, which it reads with `@Environment(AppModel.self)`.
- Core/Alarm depends on Shared, uses Player, System and `YTDLPVideoDetails` only through the alarm protocols, and
  reaches the rest of the app only through `AlarmHost` (implemented by `AppModel`).
- Player, System and Remote depend only on Shared (Remote also reads the pairing key through `PairingKey`).
- Update depends only on Shared. `StowApp` creates `AppUpdater` and `YtDlpUpdater`, gives them the alarm gate and the
  log, and puts them in the SwiftUI environment (optional there, so previews and tests work without them); the UI
  reads them with `@Environment(AppUpdater.self) var updater: AppUpdater?`. `ToolLocator` prefers `AppPaths.binDirectory`.
- `StowApp` is the only place that names the concrete services (`SelfTest` also uses `YouTubeClient`, with a fixed fake account and a temporary store;
  `AlarmDryRun` also uses `MPVPlayer`, `CoreAudioOutputs`, `BluetoothSpeaker` and `YTDLPVideoDetails`, wrapped so nothing changes).

## Data flow

```
 Timer(30m) / didWake / "Check now"
            │
        CheckScheduler ──▶ AppModel.check
                             │ account.refresh()  → re-export cookies.txt, SignInState
                             │ youtube.fetchPublicVideos(id)           (UULF RSS)
                             │ youtube.fetchMembersVideos(id, cookies) (UUMF, if signed in)
                             │ VideoDiffer.diff(sources, seen, checkedFeeds) → new videos
                             ▼
                   state.json (seen, inbox, lastCheck), log.json, notifications
                             │
                         UI observes AppModel
```

- First-add rule: a new channel (no `seenVideoIds` entry, including one added to settings.json by
  hand) puts its 2 newest videos across both feeds in the Inbox; undated members videos rank below
  dated public ones. `checkedFeeds` records which feeds of a channel have been fetched; a feed fetched
  for the first time on a known channel (members after signing in) adds its 2 newest. A feed that was
  fetched before adds every unseen video, however long the Mac was off.
- Members-only videos come from the UUMF playlist (members-only long-form; UUMO would include
  members Shorts). Every yt-dlp run (and the alarm's mpv) gets a private 0600 copy of cookies.txt
  (`CookieCopy`, Shared), in a 0700 `cookie-copies/` folder next to cookies.txt. Copies are removed after
  each run, at launch, at sign out and at quit (running yt-dlp and mpv processes are terminated first). Flat-playlist entries have no date,
  so newly found ones sort as newest in the Inbox. A channel without a members playlist returns [].
- Signed in means youtube.com has LOGIN_INFO plus SAPISID, __Secure-1PAPISID or __Secure-3PAPISID,
  the same test yt-dlp uses. The sign-in window reports success only when that session changes while
  it is open, so a stale session never counts.
- The sign-in becomes `.expired` (one notification) when yt-dlp rejects the cookies, even if it still
  lists the playlist (those videos are kept), or when the session disappears from the data store
  without the user signing out. It stays expired until a members feed accepts the cookies or the user
  signs in or out. Checks that started before a sign-in or sign-out don't change the sign-in state.
- Notifications for problems are rate-limited to one per title every 6 hours. Members feed failures
  (other than network errors and timeouts) notify right away; any check errors notify once
  `failedCheckStreak` (state.json) reaches 3 checks in a row, and recovery is logged.
- A check requested while one is running (sign-in, Check Now, wake) runs right after it.
- Live and upcoming videos are skipped. RSS reports `liveStatus = .unknown`, which is accepted.
- `AppModel.channels`, `inbox` and `lastCheck` are computed from private `AppSettings`/`AppState`
  values (still observed). Besides the contract init, `AppModel` has an internal
  `init(youtube:account:store:notifier:cookiesFile:)` used by tests and the self-test.
- settings.json is re-read before each check or mutation when its modification date changes, so
  hand edits apply without a relaunch (`checkIntervalMinutes`, minimum 5, restarts the timer).
  Saving keeps keys the app doesn't know, at the top level and per channel.
  A malformed file is renamed to `settings.corrupt-<epoch>.json`. Defaults are written on first launch.
- `launchAtLogin` in settings.json is the source of truth and is applied at every launch.

## Updates

Stow for Mac ships as GitHub pre-releases of kimdobinn/stow tagged `mac-v<version>`, made by `mac/release.sh`
(pre-releases, so Obtainium, which reads `/releases/latest`, keeps seeing the Android release). Each has
`Stow-Mac-<version>.zip` (`ditto -c -k --keepParent Stow.app`), `Stow-Mac-<version>.zip.sha256`, and a
`SHA-256: <hex>` line at the end of the notes.

`AppUpdater` (Account › Updates; "Update" badge on Account in the sidebar):
- Reads `https://api.github.com/repos/kimdobinn/stow/releases?per_page=100` unauthenticated at launch (after 20 s) and
  then hourly when the last check (UserDefaults `updates.lastChecked`) is a day old, or on "Check for Updates". It keeps
  mac-v* tags that aren't drafts and have a zip, takes the highest version (numeric, `DottedVersion`) and offers it
  when it's above `CFBundleShortVersionString`. What it found is remembered (`updates.latestRelease`) until the next check.
- "Update and Relaunch": refused while the alarm runs or within 10 minutes of it (`UpdateGate`, checked again before the
  swap). Otherwise: the zip is downloaded (progress) into a staging folder on the same volume as the app
  (`.itemReplacementDirectory`), checked against the notes' SHA-256 (else the .sha256 asset; with neither, no checksum),
  unzipped with ditto, com.apple.quarantine removed from every file, and checked: same bundle id, the advertised version,
  `codesign --verify --deep --strict`, and `SecStaticCodeCheckValidity` (all architectures, nested code, strict) against
  `anchor apple generic and certificate leaf[subject.OU] = "<team>"` with the running app's team (LYD6WV79Y4).
  An unsigned running copy can't update.
- The swap is one `renamex_np(RENAME_SWAP)` of the new bundle with `Bundle.main.bundleURL` (two renames with rollback
  where that isn't supported). A detached `/bin/sh` helper waits for this process to exit, runs `open -n` on the app and
  deletes the staging folder (which now holds the old copy); then the app quits. If the helper can't start, the swap is
  undone. Any failure before that leaves the app as it was and shows (and logs) why.

`YtDlpUpdater` keeps `~/Library/Application Support/Stow/bin/yt-dlp`, the official standalone `yt-dlp_macos` from
github.com/yt-dlp/yt-dlp/releases/latest:
- At launch it runs `bin/yt-dlp --version`; a copy that doesn't run is deleted, so Homebrew's is used.
- Then (and hourly, when the last check, UserDefaults `ytdlp.lastChecked`, is a day old; or on "Update Now") it reads
  the latest release, and when that's newer, downloads `yt-dlp_macos` to `bin/yt-dlp.download`, checks it against the
  release's `SHA2-256SUMS`, makes it executable, removes quarantine, runs `--version`, and renames it over `bin/yt-dlp`
  (running yt-dlp processes keep the old file). Never while the alarm runs or is within 10 minutes.
- `ToolLocator.url(for:)` looks in `AppPaths.binDirectory` first, so every yt-dlp run (and mpv's lookups through
  `StreamCache.wrapper`) uses Stow's copy when present; any failure leaves Homebrew's as the fallback. The standalone
  build finds ffmpeg and deno on the child PATH like Homebrew's.

Testing: Debug builds, and builds made with `SWIFT_ACTIVE_COMPILATION_CONDITIONS=STOW_TEST_OVERRIDES`, read
`STOW_UPDATE_FEED_URL` (a JSON list like GitHub's) instead of GitHub, and have `Stow --update-test <report file>`: the whole
update headless (no settings, state or UserDefaults), relaunching the new copy with the same arguments so it reports its
version. Network test of the real yt-dlp download: `TEST_RUNNER_STOW_NETWORK_TESTS=1` (`YtDlpUpdaterTests`).

## Self-test

`Stow.app/Contents/MacOS/Stow --selftest` shows no UI. It resolves @JackhopkinsCEO and @TQQQCRAZY,
reads each public and members feed (with a copy of the real cookies.txt if present, otherwise an
empty cookie jar), then runs AppModel's add/seed/check pipeline against a temporary directory. It
prints a summary and exits 0 or 1. It never writes to Application Support (its cookie copies go in the temporary directory).

`Stow --alarm-dryrun` (Debug and Release) is described under Alarm below. Debug builds also have
`Stow --snapshot <dir>`, which renders every sidebar section (plus the whole Alarm form and a running alarm)
to PNGs from a temporary copy of settings and state, with `AlarmServices.sample` devices.

## Files (~/Library/Application Support/Stow/)

All files are pretty-printed JSON with sorted keys and ISO 8601 dates, and are written atomically.

`settings.json` is hand-editable. A missing key falls back to its default:
```json
{
  "channels" : [
    { "avatarURL" : "https://…", "handle" : "@JackhopkinsCEO", "id" : "UC-XMoeMXbYrMlvmyLSwDd3g",
      "morning" : true, "phone" : true, "title" : "Jack Hopkins" }
  ],
  "checkIntervalMinutes" : 30,
  "launchAtLogin" : true,
  "schemaVersion" : 1
}
```
The `alarm` section is described under Alarm below. Unknown keys are kept when the app saves: at the top level,
inside object sections such as `alarm`, and per channel.

`state.json` is written by the app:
```json
{
  "inbox" : [ { "foundAt" : "2026-11-19T08:00:00Z", "video" : { "channelId" : "UC…", "channelTitle" : "…",
      "id" : "dQw4w9WgXcQ", "isMembersOnly" : false, "liveStatus" : "unknown",
      "publishedAt" : "2026-11-19T07:00:00Z", "thumbnailURL" : "https://…", "title" : "…" } } ],
  "lastCheck" : { "channelsChecked" : 2, "errors" : [], "finishedAt" : "…", "newVideos" : 1,
                  "startedAt" : "…", "trigger" : "scheduled" },
  "checkedFeeds" : { "UC…" : [ "uploads", "members" ] },
  "failedCheckStreak" : 0,
  "seenVideoIds" : { "UC…" : [ "newest id", "…" ] },
  "alarmPlayedIds" : [ "newest id", "…" ],
  "watchedIds" : [ "newest id", "…" ],
  "lastAlarmRun" : { "trigger" : "scheduled", "scheduledFor" : "2026-11-20T00:00:00Z",
                     "startedAt" : "2026-11-19T23:57:00Z", "endedAt" : "2026-11-20T00:41:12Z",
                     "videoIds" : [ "dQw4w9WgXcQ" ], "output" : "JBL Go 3", "outcome" : "played" },
  "lastScheduledAlarm" : "2026-11-20T00:00:00Z"
}
```

`log.json` is a capped array (newest last on disk), with entries of the form `{ "date", "id", "level": "info|warning|error", "message" }`.

`bin/yt-dlp` is Stow's own yt-dlp (see Updates).

`cookies.txt` is a Netscape cookie file for `.youtube.com` and `.google.com`, with mode 0600. It is written by Account and read by yt-dlp.

## Alarm (milestone 2)

At the configured time on the configured weekdays (default 08:00, Mon–Fri) the Mac plays the morning's videos
fullscreen with sound, streamed live from YouTube by mpv (ad-free: raw streams; nothing is stored).

### Flow

```
 AlarmController.start()  (from AppModel.start)
   │ power.holdSystemAwake(enabled)           IOPMAssertion against idle system sleep (display may sleep)
   │ keep-alive on the speaker's output       near-silent signal so the JBL doesn't auto-power-off;
   │                                          restarted on outputs/speaker changes(), stopped when it disappears
   │ AlarmSchedule.nextFire(...)              re-computed on settingsDidChange(), wake, and every 20 s
   ▼                                          (host.currentSettings() picks up hand edits)
 T − 3 min  PREP  (phase .preparing)
   │ speaker.connect(address, timeout)        if its output isn't there yet
   │ host.refreshForAlarm()                   a normal feed check (trigger "alarm"): fresh Inbox + recentVideos
   │ AlarmPlanner: candidates                 Inbox videos of channels with morning == true, not in alarmPlayedIds,
   │                                          ordered by `order`, then fallback rules if none
   │ videoDetails.details(ids, cookies)       yt-dlp -J per candidate (3 at a time): duration, live status, playable
   │ AlarmPlanner: final playlist             drop unplayable / live / upcoming / longer than maxDurationMinutes,
   ▼                                          take maxVideos; if that empties it, retry with the next rules
 T  RUN  (late-wake rule, decided when the alarm is noticed: more than 10 min after T → skip, log, "skippedLate")
   │ power.wakeDisplay()                      first, so the monitor's DisplayPort audio is back (waits up to 8 s)
   │ output = speaker's output ?? fallbackOutput by name ?? "Mac mini Speakers" ?? system default   (logged)
   │ outputs.setVolume(volume/100, output)    no fade-in; the previous volume is put back when the run ends
   │ player.play(playlist, output UID, host.playbackCookiesFile)  → PlayerEvent stream   (phase .starting/.playing)
   │   .started        → host.recordAlarmRun(outcome .running) so a crash never replays it
   │   .videoEnded     → watched when position ≥ 90% of duration
   │   .exited         → done
   │ watchdog: no video started 90 s after mpv started (or after the last load failure) → stop mpv;
   │           the whole run is cut off after videos × maxDurationMinutes + 30 min
   │ nothing started / nothing to play / player threw
   │   → sound.play(output, 10 min) at the same volume + notification   (phase .alarmSound, outcome "alarmSound")
   ▼
 host.recordAlarmRun(final record, watchedIds)  → lastAlarmRun, alarmPlayedIds, watchedIds, played videos leave the Inbox
 host.logAlarm(...)                             → log.json
```

"Test alarm now…" runs prep and run immediately (trigger `test`). It is recorded as `lastAlarmRun`, but only the videos it
played to ≥ 90 % become alarm-played and leave the Inbox, so a test doesn't use up the morning's videos. A scheduled
alarm that comes due during a test stops the test and runs. "Stop Alarm"
(button, toolbar indicator, ⌘.) cancels prep, stops mpv and the alarm sound.

Details of the engine (`Core/Alarm/`):
- `AlarmController` owns the phase, the schedule (`AlarmScheduler`: a 20 s timer plus `NSWorkspace.didWakeNotification`,
  with an App Nap–proof activity while armed) and `AlarmDevices` (outputs, paired devices, `SpeakerStatus`, keep-alive and
  its restarts on device changes). `AppModel+Alarm.swift` reaches devices through `alarm.devices` and the next alarm
  through `alarm.nextFireDate(for:)`.
- `AlarmSchedule` is pure: the alarm keeps its wall-clock time across DST changes, a time skipped by spring-forward fires
  at the first valid minute after it, and a time repeated at fall-back fires once. Prep starts 3 min before; up to
  10 min late still runs; later is skipped (`skippedLate`). Alarm times from before the app launched (more than 10 min),
  or from before the Mac started up (someone switched it on), are ignored, and `state.lastScheduledAlarm` stops a
  relaunch from running an alarm twice.
- Prep limits: speaker connect 20 s (then up to 10 s for its CoreAudio output), feed check awaited at most 120 s,
  video checks at most 150 s (after that the unchecked plan plays), 60 s per `yt-dlp -J`. Both share the time until
  20 s after the alarm: the feed check is skipped when it would leave the video check less than 60 s (an alarm noticed
  late), and the video check always gets at least 20 s. At most 12 lookups per run, of which each fallback rule with
  candidates keeps up to 3, so rejected Inbox videos can't starve the rules. The connect is tried once per run.
- A run stopped before anything played is recorded as `stopped` with "Stopped before anything played.".
- Hand edits to "alarm" that can't be read (or unknown day names, rules without a known kind) are replaced by defaults
  and reported in the Log and a notification. An unreadable `enabled` turns the alarm off. Day names may be written
  in full ("Monday"), times as "7:30 am" or "07.30", `enabled` as "yes"/"off"/1/0.
- The fallback output may have no volume control (the monitor's DisplayPort audio): `setVolume` then fails, is logged,
  and the alarm plays at the device's own level. `setVolume` also unmutes the device.
- The first time the app lists Bluetooth devices macOS asks for Bluetooth permission. Denied, the alarm still finds the
  speaker's CoreAudio output by address/name, but can't connect it.

### Player (mpv)

`/opt/homebrew/bin/mpv --no-config --fs --native-fs=no --ontop --force-window=immediate --title="Stow Alarm"
--audio-device=coreaudio/<UID> --volume=100 --input-ipc-server=<socket>
--script-opts=ytdl_hook-ytdl_path=/opt/homebrew/bin/yt-dlp --ytdl-format='bv*[height<=1080][fps<=60]+ba/b'
[--ytdl-raw-options=cookies=<CookieCopy>] <watch URLs…>`. The player observes `time-pos` over IPC to skip
SponsorBlock segments (`sponsor.ajay.app/api/skipSegments`, categories sponsor, selfpromo, interaction, intro,
outro; 404 or any failure = no skipping), and draws a clock plus "1/3 · title · channel" with `osd-overlay` (ASS),
shown for a few seconds at each video start and refreshed about every 15 s. mpv's default keys work (space, >, q).
`MPVPlayer.terminateAll()` runs at quit.

- Overlay: the "1/3 · title · channel" banner is top-left for 6 s at each video start; the clock is top-right,
  redrawn at each minute boundary and at least every 15 s.
- Events: `.started` comes at mpv's first `playback-restart` of an entry (first frame or audio), not at file load.
  `.videoEnded.position` is the furthest `time-pos` reached (a SponsorBlock skip counts up to the segment end; at
  end of file it is slightly short of the duration). An entry that ends with an error before starting yields
  `.loadFailed` with yt-dlp's message. Exit: `stop()`, q or a closed window → `.stopped`; otherwise `.finished` if
  anything started, else `.failed`. If mpv exits before its IPC socket appears, `play` throws. Cancelling the
  event stream's consumer stops mpv.
- The alarm sound is `/System/Library/Sounds/Glass.aiff` (macOS 26 has no Radar.aiff), looped by `AVAudioPlayer`
  with `currentDevice` set to the output's UID.
- `MPVPlayer(extraArguments:)` appends options after the standard ones; tests and the dry run pass
  `--vo=null --ao=null --force-window=no --fs=no --ontop=no --length=…` so nothing is seen or heard.

### Dry run

`Stow.app/Contents/MacOS/Stow --alarm-dryrun` (Debug and Release) runs the whole alarm headless without any effect:
1. Copies settings.json, state.json and cookies.txt into a temporary directory (deleted at the end) and builds an
   `AppModel` on it, so the feed check, yt-dlp and mpv (cookie copies included) only write there.
2. Prints the alarm settings, the next scheduled alarm, the planner's rounds and the Up next preview.
3. Lists the CoreAudio outputs (with volumes), the paired Bluetooth audio devices (only when this process already has
   Bluetooth permission: IOBluetooth aborts a terminal-launched process otherwise), whether the speaker's output is
   there, and the output the alarm would use.
4. Runs `AlarmRunner` (trigger `test`) with `AlarmServices.dryRun`: the real outputs list, yt-dlp details and mpv, but
   volume, display wake, Bluetooth connect and the alarm sound only print what they would do. mpv gets
   `--vo=null --ao=null --force-window=no --fs=no --ontop=no --length=10`, and the run is stopped 20 s after the
   first video starts (90 s if none starts). It prints every log line, each video's SponsorBlock segments, every
   `PlayerEvent`, and the `AlarmRunRecord` it would save.
5. Exits 0 when the outcome is `played`, else 1.

### settings.json "alarm"

Every key is optional and falls back to its default on its own; a malformed value never discards the rest of the file.
Out-of-range numbers are clamped, unknown day names and rules with an unknown `kind` are dropped.

```json
"alarm" : {
  "enabled" : true,
  "time" : "08:00",
  "days" : [ "mon", "tue", "wed", "thu", "fri" ],
  "maxVideos" : 3,
  "order" : "oldestFirst",
  "volume" : 80,
  "maxDurationMinutes" : 60,
  "fallbackRules" : [
    { "kind" : "mostRecentUnplayed", "channelId" : null, "withinDays" : 7 },
    { "kind" : "randomUnplayed", "channelId" : "UC-XMoeMXbYrMlvmyLSwDd3g", "withinDays" : 30 },
    { "kind" : "replayLatest", "channelId" : null }
  ],
  "speaker" : { "name" : "JBL Go 3", "address" : "40:C1:F6:88:8F:AF", "keepAlive" : true, "keepAliveLevel" : -60 },
  "fallbackOutput" : "Mi monitor"
}
```

| Key | Values | Default |
|---|---|---|
| `time` | "HH:mm", 24-hour, local time | "08:00" |
| `days` | any of mon tue wed thu fri sat sun; [] = never | mon–fri |
| `maxVideos` | 1–10 | 3 |
| `order` | oldestFirst, newestFirst (by publish date; Inbox candidates only) | oldestFirst |
| `volume` | 0–100, the output device's volume while the alarm plays (put back afterwards) | 80 |
| `maxDurationMinutes` | 1–600; longer videos are skipped | 60 |
| `fallbackRules` | ordered; first rule that yields a playable video wins, and a rule yields one video (only new Inbox videos fill up to `maxVideos`). `channelId` null/absent = any channel with `morning` on; an explicit `channelId` uses that channel even with `morning` off, as long as it is followed. `mostRecentUnplayed` / `randomUnplayed` take `withinDays` (1–365, default 7; publish date); `replayLatest` replays the newest video even if already played. Pool: `state.recentVideos`. `randomUnplayed` (and the Up next preview) use a generator seeded with the alarm's local day, so the preview shows that day's pick | most recent unplayed (7 days), then replay latest |
| `speaker` | `address` null = not Bluetooth (matched by name only); `keepAliveLevel` dBFS, −90…−20 | JBL Go 3 |
| `fallbackOutput` | output name used when the speaker's output is missing; then "Mac mini Speakers", then the system default | "Mi monitor" |

### State additions

`alarmPlayedIds` (newest first, at most 500): videos the alarm started; never auto-picked again (except by
`replayLatest`). `watchedIds` (newest first, at most 2000): played to ≥ 90 %, for a future phone sync.
`lastAlarmRun`: `AlarmRunRecord` {trigger, scheduledFor, startedAt, endedAt, videoIds, fallbackRule, output,
outcome (running, played, alarmSound, skippedLate, stopped, failed), error}. It is written when the first video starts
(outcome `running`, so a crash never replays it) and again when the run ends.
`lastScheduledAlarm`: the alarm time of the newest scheduled run (played or skipped), so a test run that replaces
`lastAlarmRun` can't make that morning's alarm fire again after a relaunch. Older files without it fall back to
`lastAlarmRun` when that was a scheduled run.

## Phone remote

While an alarm run is active (from prep until it ends, test alarms included) the paired phone can control it over
the home Wi-Fi, so nobody has to touch the Mac. `AlarmController` reports every phase to `AlarmServices.remote`
(`AlarmRemote`), which serves plain HTTP/1.1 on port 48261 (any free port when it is taken), advertised over Bonjour
as `_stow-remote._tcp` under the Mac's name. It listens only with a pairing key on disk (a phone was paired) and stops
when the run ends. macOS holds an advertising listener back until Local Network access is allowed, so if that fails
the remote listens without Bonjour (the push still carries the address); at launch, with a phone paired, it advertises
for a few seconds so macOS asks while someone is at the Mac, not first at alarm time.

- Every request is signed with the 32-byte pairing key: `X-Stow-Time` (unix ms), `X-Stow-Nonce` (32 lowercase hex),
  `X-Stow-Signature` = base64url (no padding) of HMAC-SHA256 over `METHOD\nPATH\nTIME\nNONCE\nhex SHA-256(body)`
  (PATH without the query). More than 120 s off the Mac's clock, a nonce seen in the last 5 minutes (in any run), or a
  bad signature → 401. An action reaching a run's server after that run ended → 409. One request per connection (`Connection: close`), bodies by `Content-Length` only (no chunked),
  at most 64 KB (413).
- `GET /v1/state` (phase, playlist, what plays, the output and its volume), `GET /v1/choices` (Inbox and recent videos,
  newest first, at most 40), `POST /v1/action` (`setPaused`, `seekBy`, `seekTo`, `next`, `playIndex`, `playVideo`,
  `setVolume`, `setMuted`, `stop`) answering with the state; 400 bad input, 404 unknown path, 405 wrong method,
  409 not applicable (before the videos play only `stop` and `setVolume` work).
- `setVolume` is the alarm output's own volume (before the output is chosen it replaces the configured volume); the
  previous volume still comes back when the run ends. `setMuted` is the player's mute, like the window's. `stop` is
  Stop Alarm. `playIndex`/`playVideo` jump with mpv's `playlist-play-index` and unpause; `playVideo` of a video not in
  the playlist appends it (`loadfile … append`), and the runner adds it to the playlist and the run record when it starts.
- When the run first reaches `starting`/`playing` and the server listens, every paired phone gets an FCM data message
  `{type: alarm, state: playing, port, hosts, macName}` (`hosts`: the Mac's IPv4 addresses, LAN first); when it ends,
  `{type: alarm, state: ended}` (only after a `playing` one). Pushes go through `AlarmHost.pushToPhones` →
  `PhoneSync.pushToPhones`, leave one after another in order, are best effort and only logged when they fail. Actions and the first rejected request of
  a run are logged; polling isn't.
- Debug builds: `Stow --remote-demo [--remote-key <base64url>]` runs a test alarm on the two newest known public videos
  through the real engine and remote (port 48261, Bonjour), headless and silent (no window, `--ao=null`), with the
  volume in memory, no pushes, no cookies and nothing saved. It prints every phase, request and push, and ends on
  `stop`, when the videos finish, or after 10 minutes.
